# Task Economy Schema — Deflationary Daily Design

## 1. Анализ текущего состояния

### Что есть сейчас
- **taskConfig.js** — хардкод задач с плоскими credits (один балл на действие)
- **transactions** — таблица для earn/burn; при клике на задачу вставляется строка с `amount = credits`
- **dailyBase** (store) — клиентский счётчик «выполнено сегодня» по actionId; сбрасывается при новом дне
- **Нет таблицы задач в БД** — все определения в коде

### Проблемы текущей экономики
| Задача | Текущие credits | Проблема |
|--------|-----------------|----------|
| Проснулся сам | 30 | Высокий базовый балл |
| Сделал уроки | 50 | Очень высоко |
| Оценка 5+ | 50 | Повторяемо, легко набрать 200+ |
| Спать вовремя | 50 | |
| Завтрак + модификаторы | 20+10+5+10 = 45 | За один приём |
| **Идеальный день** | **~350+** | Инфляция, нет дефицита |

### Проблемы архитектуры
1. **Нет time_block** — нельзя ограничить «утренние» задачи по времени
2. **Нет max_daily_completions** — можно спамить одну задачу
3. **Нет base vs bonus** — всё в одном поле, сложно моделировать «съел всё» как бонус
4. **Нет category** — группировка только в UI, не в данных
5. **Валидация только на клиенте** — dailyBase в памяти, при сбросе/баге можно обойти

## 2. Рекомендации UX/Архитектуры

### 2.1 Разделение ответственности
| Слой | Роль |
|------|------|
| **task_definitions** | Каталог задач: time_block, category, base_reward, bonus_reward, max_daily_completions |
| **transactions** | Факты выполнения: user_id, task_definition_id, amount, created_at |
| **RPC / triggers** | Проверка лимитов на сервере перед insert |

### 2.2 Дефляционная экономика
- **Цель**: идеальный день ≈ 100–150 очков
- **Стратегия**: низкие base (5–20), умеренные bonus (10–20), жёсткие max_daily_completions
- **Формула**: `total_possible_day = Σ (base_reward × min(completions, max_daily_completions)) + bonus_reward × …`

### 2.3 time_block
- **morning** — до ~12:00 (или до обеда)
- **afternoon** — 12:00–18:00
- **evening** — после 18:00
- **anytime** — без ограничения

Проверка time_block может быть на клиенте (UX) или в RPC (строго). Для MVP — клиент, позже — сервер.

### 2.4 category
- **routine** — утро, постель, зубы
- **food** — приёмы пищи + бонусы
- **school** — уроки, портфель, оценки
- **bonus** — доп. занятия, помощь по дому

### 2.5 Связь task_definitions ↔ transactions
- Добавить в `transactions` колонку `task_definition_id` (nullable)
- Для earn-транзакций: при наличии `task_definition_id` — валидировать лимиты через RPC
- Для burn/списаний: `task_definition_id = null`

### 2.6 Обратная совместимость
- Старые транзакции без `task_definition_id` — оставить как есть
- Новый код: при завершении задачи передавать `task_definition_id`, RPC проверяет лимиты
